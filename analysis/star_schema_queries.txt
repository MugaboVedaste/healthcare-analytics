# Star Schema Queries

## Question 1: Monthly Encounters by Specialty

### The SQL (optimized for star schema)

```sql
SELECT
    d.year_number AS encounter_year,
    d.month_number AS encounter_month,
    s.specialty_name,
    et.encounter_type_name,
    COUNT(DISTINCT fe.encounter_id) AS total_encounters,
    COUNT(DISTINCT fe.patient_key) AS unique_patients
FROM fact_encounters AS fe
JOIN dim_date AS d
    ON fe.encounter_date_key = d.date_key
JOIN dim_specialty AS s
    ON fe.specialty_key = s.specialty_key
JOIN dim_encounter_type AS et
    ON fe.encounter_type_key = et.encounter_type_key
GROUP BY
    d.year_number,
    d.month_number,
    s.specialty_key,
    s.specialty_name,
    et.encounter_type_key,
    et.encounter_type_name
ORDER BY
    encounter_year,
    encounter_month,
    s.specialty_name,
    et.encounter_type_name;
```

### 1. Execution time estimate

- Star schema: ~0.175 ms
- Original OLTP schema: ~0.123 ms

### 2. Improvement factor

The star schema was approximately **1.42× slower** on this sample dataset.

Calculation: 0.175 / 0.123 ≈ 1.42.

### 3. Explanation

The fact table stores the specialty, patient, encounter type, and date keys needed for analysis. This avoids joining the OLTP providers table to retrieve the specialty. The date dimension provides year and month attributes for grouping.

However, the star schema was not faster in this test. With only four encounters, the overhead of grouping, sorting, and accessing dimension tables can outweigh the benefits of dimensional modeling.

## Question 2: Top Diagnosis–Procedure Pairs

### The SQL (optimized for star schema)

```sql
SELECT
    d.icd10_code,
    d.icd10_description,
    p.cpt_code,
    p.cpt_description,
    COUNT(*) AS pair_count
FROM bridge_encounter_diagnoses AS ed
JOIN dim_diagnosis AS d
    ON ed.diagnosis_key = d.diagnosis_key
JOIN bridge_encounter_procedures AS ep
    ON ed.encounter_key = ep.encounter_key
JOIN dim_procedure AS p
    ON ep.procedure_key = p.procedure_key
GROUP BY
    d.diagnosis_key,
    d.icd10_code,
    d.icd10_description,
    p.procedure_key,
    p.cpt_code,
    p.cpt_description
ORDER BY
    pair_count DESC,
    d.icd10_code,
    p.cpt_code
LIMIT 5;
```

### 1. Execution time estimate

- Star schema: ~0.957 ms
- Original OLTP schema: ~0.228 ms

### 2. Improvement factor

The star schema was approximately **4.20× slower** on this sample dataset.

Calculation: 0.957 / 0.228 ≈ 4.20.

### 3. Explanation

The bridge tables connect diagnoses and procedures through their shared encounter key. The dimension tables provide diagnosis and procedure descriptions.

MySQL uses index lookups to retrieve the related records, but it also creates a temporary table for aggregation and sorts the results to return the top five pairs. These operations add overhead. The star schema does not eliminate the joins needed to connect diagnoses and procedures, and the small dataset offers little opportunity for dimensional modeling to improve performance.

## Question 3: 30-Day Readmission Rate

### The SQL (optimized for star schema)

```sql
SELECT
    s.specialty_name,
    COUNT(DISTINCT index_enc.encounter_id) AS inpatient_discharges,
    COUNT(DISTINCT readmit.encounter_id) AS readmitted_encounters,
    ROUND(
        100.0 * COUNT(DISTINCT readmit.encounter_id)
        / NULLIF(COUNT(DISTINCT index_enc.encounter_id), 0),
        2
    ) AS readmission_rate_percent
FROM fact_encounters AS index_enc
JOIN dim_specialty AS s
    ON index_enc.specialty_key = s.specialty_key
JOIN dim_encounter_type AS et
    ON index_enc.encounter_type_key = et.encounter_type_key
LEFT JOIN fact_encounters AS readmit
    ON readmit.patient_key = index_enc.patient_key
    AND readmit.encounter_datetime > index_enc.discharge_datetime
    AND readmit.encounter_datetime <= DATE_ADD(
        index_enc.discharge_datetime,
        INTERVAL 30 DAY
    )
WHERE et.encounter_type_name = 'Inpatient'
GROUP BY
    s.specialty_key,
    s.specialty_name
ORDER BY
    readmission_rate_percent DESC,
    s.specialty_name;
```

### 1. Execution time estimate

- Star schema: ~0.322 ms
- Original OLTP schema: ~0.682 ms

### 2. Improvement factor

The star schema was approximately **2.12× faster** in this test.

Calculation: 0.682 / 0.322 ≈ 2.12.

### 3. Explanation

The fact table stores patient, specialty, and encounter type keys, allowing the query to retrieve the relevant data with fewer joins to normalized OLTP tables. The execution plan uses indexes to locate inpatient encounters and search for subsequent encounters by patient and datetime.

The self-join on the fact table is still necessary to identify readmissions. In this small dataset, the indexed lookup helps reduce the time required for that search.

## Question 4: Revenue by Specialty and Month

### The SQL (optimized for star schema)

```sql
SELECT
    d.year_number AS claim_year,
    d.month_number AS claim_month,
    s.specialty_name,
    SUM(b.allowed_amount) AS total_allowed_revenue
FROM fact_billing AS b
JOIN fact_encounters AS fe
    ON b.encounter_key = fe.encounter_key
JOIN dim_specialty AS s
    ON fe.specialty_key = s.specialty_key
JOIN dim_date AS d
    ON b.claim_date_key = d.date_key
GROUP BY
    d.year_number,
    d.month_number,
    s.specialty_key,
    s.specialty_name
ORDER BY
    claim_year,
    claim_month,
    total_allowed_revenue DESC;
```

### 1. Execution time estimate

- Star schema: ~0.275 ms
- Original OLTP schema: ~0.247 ms

### 2. Improvement factor

The star schema was approximately **1.11× slower** in this test.

Calculation: 0.275 / 0.247 ≈ 1.11.

### 3. Explanation

The billing fact table stores allowed amounts and a claim-date key. The encounter fact table connects billing records to specialties, while the date dimension provides year and month attributes.

MySQL uses primary-key lookups to retrieve the related encounters, specialties, and dates. It then creates a temporary table to aggregate revenue and sorts the results.

Although the star schema provides a clear structure for analytical reporting, it was slightly slower in this test. With only two billing records, the dataset is too small to demonstrate a meaningful performance benefit.

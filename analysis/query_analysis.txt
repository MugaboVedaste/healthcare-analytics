QUESTION 1: Monthly Encounters by Specialty

SQL Query:

```sql
SELECT
    YEAR(e.encounter_date) AS encounter_year,
    MONTH(e.encounter_date) AS encounter_month,
    s.specialty_name,
    e.encounter_type,
    COUNT(DISTINCT e.encounter_id) AS total_encounters,
    COUNT(DISTINCT e.patient_id) AS unique_patients
FROM encounters AS e
JOIN providers AS p
    ON e.provider_id = p.provider_id
JOIN specialties AS s
    ON p.specialty_id = s.specialty_id
GROUP BY
    YEAR(e.encounter_date),
    MONTH(e.encounter_date),
    s.specialty_name,
    e.encounter_type
ORDER BY
    encounter_year,
    encounter_month,
    s.specialty_name,
    e.encounter_type;
```

Schema Analysis:

- Tables joined: `encounters`, `providers`, `specialties`.
- Number of joins: 2.
- Join path: `encounters → providers → specialties`.
- Aggregations: Counts distinct encounters and distinct patients.
- Grouping: Year, month, specialty, and encounter type.
- Indexes used: The execution plan shows an index scan on `providers.specialty_id`, primary-key lookups on `specialties`, and index lookups on `encounters.provider_id`.

Performance:

- Execution time: Approximately 0.123 milliseconds (0.000123 seconds).
- Actual result rows: 4.
- Estimated rows: The plan estimated approximately 3 rows for the provider scan and approximately 3 rows entering the first nested-loop join. These are estimates, not a count of all rows scanned.
- Execution method: MySQL `EXPLAIN ANALYZE`.

Bottleneck Identified:

The query combines three normalized tables and performs joins before grouping the results. MySQL then sorts the grouped data and calculates distinct counts for encounters and patients. These operations are inexpensive with the current small sample dataset, as the measured execution time was approximately 0.123 milliseconds. However, as the number of encounters and patients increases, joins, sorting, grouping, and distinct-count calculations may require more processing time and memory.

Optimization Opportunity:

A star schema can simplify analytical queries by organizing encounter measures in a central fact table and exposing specialty, date, patient, and encounter-type attributes through dimensions. Appropriate indexes and pre-aggregated measures may reduce query work, depending on the final schema and data volume.


QUESTION 2: Top Diagnosis–Procedure Pairs

SQL Query:

```sql
SELECT
    d.icd10_code,
    d.icd10_description,
    pr.cpt_code,
    pr.cpt_description,
    COUNT(DISTINCT e.encounter_id) AS encounter_count
FROM encounters AS e
JOIN encounter_diagnoses AS ed
    ON e.encounter_id = ed.encounter_id
JOIN diagnoses AS d
    ON ed.diagnosis_id = d.diagnosis_id
JOIN encounter_procedures AS ep
    ON e.encounter_id = ep.encounter_id
JOIN procedures AS pr
    ON ep.procedure_id = pr.procedure_id
GROUP BY
    d.icd10_code,
    d.icd10_description,
    pr.cpt_code,
    pr.cpt_description
ORDER BY
    encounter_count DESC,
    d.icd10_code,
    pr.cpt_code;
```

Schema Analysis:

- Tables joined: `encounters`, `encounter_diagnoses`, `diagnoses`, `encounter_procedures`, `procedures`.
- Number of joins: 4.
- Join paths: `encounters → encounter_diagnoses → diagnoses` and `encounters → encounter_procedures → procedures`.
- Aggregations: Counts distinct encounters for each diagnosis–procedure pair.
- Grouping: Diagnosis code, diagnosis description, procedure code, and procedure description.
- Indexes used: The execution plan shows an index lookup on `encounter_diagnoses.diagnosis_id`, primary-key lookups on `encounters` and `procedures`, and an index lookup on `encounter_procedures.encounter_id`. The `diagnoses` table is scanned.

Performance:

- Execution time: Approximately 0.228 milliseconds (0.000228 seconds).
- Actual result rows: 5.
- Intermediate rows: 7 rows entered the grouping stage.
- Estimated rows: The plan estimated approximately 3 rows for the `diagnoses` table scan and approximately 3 rows for the nested-loop join stages. These are optimizer estimates, not counts of all rows scanned.
- Execution method: MySQL `EXPLAIN ANALYZE`.

Bottleneck Identified:

The query joins five normalized tables and processes diagnosis and procedure relationships before grouping the results. An encounter with multiple diagnoses and procedures can produce multiple intermediate rows. MySQL then sorts the data, calculates distinct encounter counts, and sorts the final results. These operations are inexpensive with the current small sample dataset, as the measured execution time was approximately 0.228 milliseconds. However, as the data volume grows, joins, intermediate rows, sorting, grouping, and distinct-count calculations may require more processing time and memory.

Optimization Opportunity:

A star schema can simplify analytical queries by organizing encounter-related measures in a central fact table and connecting diagnosis, procedure, and other descriptive attributes through dimensions. Appropriate indexes and a suitable fact-table design may reduce join complexity and query work. The actual performance improvement must be verified by comparing this query with its equivalent star schema query using `EXPLAIN ANALYZE`.


QUESTION 3: 30-Day Readmission Rate

SQL Query:

```sql
SELECT
    s.specialty_name,
    COUNT(DISTINCT e.encounter_id) AS total_inpatient_discharges,
    COUNT(DISTINCT CASE
        WHEN r.encounter_id IS NOT NULL THEN e.encounter_id
    END) AS readmitted_encounters,
    ROUND(
        100.0 * COUNT(DISTINCT CASE
            WHEN r.encounter_id IS NOT NULL THEN e.encounter_id
        END) / NULLIF(COUNT(DISTINCT e.encounter_id), 0),
        2
    ) AS readmission_rate_percentage
FROM encounters AS e
JOIN providers AS p
    ON e.provider_id = p.provider_id
JOIN specialties AS s
    ON p.specialty_id = s.specialty_id
LEFT JOIN encounters AS r
    ON r.patient_id = e.patient_id
    AND r.encounter_date > e.discharge_date
    AND r.encounter_date <= DATE_ADD(
        e.discharge_date, INTERVAL 30 DAY
    )
WHERE e.encounter_type = 'Inpatient'
    AND e.discharge_date IS NOT NULL
GROUP BY s.specialty_id, s.specialty_name
ORDER BY readmission_rate_percentage DESC;
```

Schema Analysis:

- Tables joined: `encounters` (twice), `providers`, `specialties`.
- Number of joins: 3, including a self-join on `encounters`.
- Join path: `encounters → providers → specialties`, with a self-join matching subsequent encounters for the same patient.
- Aggregations: Counts eligible inpatient discharges and distinct encounters followed by a readmission, then calculates the readmission rate as a percentage.
- Grouping: Specialty ID and specialty name.
- Indexes used: The execution plan shows primary-key lookups on `providers` and `specialties`, and an index range scan on the second `encounters` reference to find potential readmissions.
- Readmission detection: A subsequent encounter must belong to the same patient, occur after the original discharge, and take place within 30 days of discharge.

Performance:

- Execution time: Approximately 0.682 milliseconds (0.000682 seconds).
- Actual result rows: 1 specialty group.
- Estimated rows: The plan estimated 4 rows for the original `encounters` table scan, 1 row after filtering eligible inpatient discharges, and approximately 4 rows for the readmission index range scan. These are optimizer estimates, not counts of all rows scanned.
- Actual rows processed: The original `encounters` table scan examined 4 rows, and the readmission index range scan examined 4 rows but found no matching readmission for the eligible encounter.
- Execution method: MySQL `EXPLAIN ANALYZE`.

Bottleneck Identified:

The query uses a self-join on `encounters` to identify subsequent encounters for the same patient within 30 days of discharge. MySQL scans the original encounters, filters eligible inpatient discharges, and performs an index range scan to find potential readmissions. The query then groups the results, calculates distinct counts, and sorts the readmission rates. These operations may become expensive as the number of encounters increases, particularly if many records must be examined for each eligible discharge. With the current small sample dataset, the measured execution time is approximately 0.682 milliseconds, so this does not demonstrate a significant performance problem.

Optimization Opportunity:

A composite index on `(patient_id, encounter_date)` may improve the search for subsequent encounters belonging to the same patient within the 30-day window. Its effectiveness should be verified using `EXPLAIN ANALYZE`. A star schema may also support analytical reporting by organizing encounter information in a central fact table with relevant dimensions. Any performance improvement must be measured against the original OLTP query.

QUESTION 4: Revenue by Specialty and Month

SQL Query:

```sql
SELECT
    YEAR(b.claim_date) AS claim_year,
    MONTH(b.claim_date) AS claim_month,
    s.specialty_name,
    SUM(b.allowed_amount) AS total_revenue,
    COUNT(DISTINCT b.billing_id) AS total_claims
FROM billing AS b
JOIN encounters AS e
    ON b.encounter_id = e.encounter_id
JOIN providers AS p
    ON e.provider_id = p.provider_id
JOIN specialties AS s
    ON p.specialty_id = s.specialty_id
GROUP BY
    YEAR(b.claim_date),
    MONTH(b.claim_date),
    s.specialty_id,
    s.specialty_name
ORDER BY
    claim_year,
    claim_month,
    s.specialty_name;
```

Schema Analysis:

- Tables joined: `billing`, `encounters`, `providers`, `specialties`.
- Number of joins: 3.
- Join path: `billing → encounters → providers → specialties`.
- Aggregations: Calculates total revenue using `SUM(b.allowed_amount)` and counts distinct billing claims.
- Grouping: Claim year, claim month, specialty ID, and specialty name.
- Indexes used: The execution plan shows primary-key lookups on `encounters`, `providers`, and `specialties`. The `billing` table is scanned.

Performance:

- Execution time: Approximately 0.247 milliseconds (0.000247 seconds).
- Actual result rows: 2.
- Estimated rows: The plan estimated approximately 2 rows for the `billing` table scan and approximately 2 rows entering the join stages. These are optimizer estimates, not counts of all rows scanned.
- Execution method: MySQL `EXPLAIN ANALYZE`.

Bottleneck Identified:

The query joins four normalized tables and aggregates billing amounts by claim month and specialty. MySQL scans the billing table, performs primary-key lookups for related encounters, providers, and specialties, and then sorts and groups the results. These operations are inexpensive with the current small sample dataset, as the measured execution time was approximately 0.247 milliseconds. However, as billing records increase, table scans, joins, sorting, and aggregation may require more processing time and memory.

Optimization Opportunity:

A star schema can simplify analytical queries by organizing billing measures in a central fact table and connecting date and specialty attributes through dimensions. Appropriate indexes and pre-aggregated revenue measures may reduce query work, depending on the final schema and data volume. The performance improvement must be verified by running the equivalent query against the star schema and comparing execution times and execution plans.

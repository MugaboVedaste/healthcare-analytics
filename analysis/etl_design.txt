# ETL Design — Healthcare Analytics Data Warehouse

## 1. Overview

The ETL (Extract, Transform, Load) process transfers data from the normalized OLTP database, `healthcare_analytics`, into the dimensional data warehouse.

**Source database:** `healthcare_analytics`

**Target database:** `healthcare_analytics_dw` (the database selected by the current ETL script; confirm this matches the database name used in `star_schema.sql`).

**ETL script:** `etl_load.sql`

**Platform:** MySQL 8.0+

The ETL process performs the following operations:

1. Resets the existing warehouse tables.
2. Generates a complete date dimension.
3. Inserts unknown dimension members.
4. Loads descriptive dimensions from the OLTP database.
5. Creates staging tables containing pre-aggregated encounter metrics.
6. Loads the encounter fact table using warehouse surrogate keys.
7. Calculates readmission indicators.
8. Loads diagnosis and procedure bridge tables.
9. Builds the monthly diagnosis–procedure aggregate table.
10. Performs reconciliation checks and records the ETL batch status.

The current implementation uses a full-refresh loading strategy.

## 2. Dimension Load Logic

### 2.1 Loading `dim_date`

**Source:** Generated calendar dates.

**Target:** `dim_date`

**Approach:**

1. Generate every calendar date from January 1, 2015, through December 31, 2035.
2. Generate `date_key` using the `YYYYMMDD` format.
3. Populate calendar attributes, including year, quarter, month, month name, year-month label, day, weekday, week number, and weekend indicator.
4. Calculate fiscal year and fiscal quarter, assuming the fiscal year starts on July 1.
5. Insert an additional unknown date member with key `-1`.

The implementation uses a recursive common table expression (CTE) to generate the calendar dates.

The date dimension contains a continuous calendar range rather than only dates found in the source tables. This ensures that dates without corresponding healthcare activity are also available for reporting.

### 2.2 Loading Unknown Dimension Members

Before loading source dimension records, the ETL inserts an unknown member with surrogate key `-1` into the following dimensions:

- `dim_patient`
- `dim_specialty`
- `dim_department`
- `dim_provider`
- `dim_encounter_type`
- `dim_diagnosis`
- `dim_procedure`

These records provide default dimension references for missing or unmatched source values.

This approach allows fact records to retain their relationships with dimension tables even when the corresponding source information is unavailable.

### 2.3 Loading `dim_patient`

**Source:** `healthcare_analytics.patients`

**Target:** `dim_patient`

**Approach:**

1. Extract patient records from the source `patients` table.
2. Load the original `patient_id` and MRN.
3. Generate descriptive attributes, including full name and gender description.
4. Extract the birth year from the date of birth.
5. Calculate the patient's current age group using the date of birth and the ETL execution date.
6. Generate a row hash using selected patient attributes.

The age groups are:

- `0-17`
- `18-39`
- `40-64`
- `65-79`
- `80+`
- `Unknown`

The `row_hash` is generated using MD5 over selected patient attributes. It can support future change detection.

The current ETL performs an initial full load after truncating the dimension table. It does not implement historical patient versions.

### 2.4 Loading `dim_specialty`

**Source:** `healthcare_analytics.specialties`

**Target:** `dim_specialty`

**Approach:**

1. Extract specialty identifiers and codes.
2. Extract specialty names.
3. Replace missing specialty names with `Unknown`.
4. Insert the records into the warehouse dimension.

The dimension stores the original specialty identifier alongside its warehouse-generated surrogate key.

### 2.5 Loading `dim_department`

**Source:** `healthcare_analytics.departments`

**Target:** `dim_department`

**Approach:**

1. Extract department identifiers.
2. Extract department names, floor, and capacity.
3. Replace missing department names with `Unknown`.
4. Insert the records into the warehouse dimension.

### 2.6 Loading `dim_encounter_type`

**Source:** Distinct encounter types from `healthcare_analytics.encounters`

**Target:** `dim_encounter_type`

**Approach:**

1. Extract distinct non-null encounter types.
2. Assign a standardized encounter type code.
3. Generate indicators identifying inpatient and emergency encounters.
4. Insert the distinct encounter types into the dimension.

The implemented encounter type codes include:

| Encounter type | Code |
|---|---|
| Inpatient | IP |
| Outpatient | OP |
| ER | ER |
| Other | OTH |

The dimension also stores `is_inpatient` and `is_emergency` indicators, which support analytical filtering, particularly readmission analysis.

### 2.7 Loading `dim_provider`

**Source:** `healthcare_analytics.providers`, `specialties`, and `departments`

**Target:** `dim_provider`

**Approach:**

1. Extract provider identifiers, names, and credentials.
2. Retrieve the provider's specialty and department information.
3. Generate the provider's full name.
4. Generate a row hash using selected provider attributes.
5. Set the initial effective start date to `1900-01-01`.
6. Set the effective end date to `9999-12-31`.
7. Mark the initial provider record as current.

The provider dimension is designed to support **Slowly Changing Dimension Type 2 (SCD Type 2)**.

This approach allows historical provider versions to be preserved when provider attributes change.

The current script establishes the initial SCD Type 2 records, but it does not yet implement the complete change-detection process that expires an old version and inserts a new version during subsequent incremental runs.

### 2.8 Loading `dim_diagnosis`

**Source:** `healthcare_analytics.diagnoses`

**Target:** `dim_diagnosis`

**Approach:**

1. Extract diagnosis identifiers.
2. Load ICD-10 codes and descriptions.
3. Derive the ICD-10 chapter from the first character of the code.
4. Derive the ICD-10 category from the first three characters of the code.
5. Insert the resulting records into the warehouse.

### 2.9 Loading `dim_procedure`

**Source:** `healthcare_analytics.procedures`

**Target:** `dim_procedure`

**Approach:**

1. Extract procedure identifiers.
2. Retrieve CPT codes and descriptions.
3. Insert the records into the warehouse dimension.

## 3. Fact Table Load Logic

### 3.1 Loading `fact_encounters`

**Source:** `healthcare_analytics.encounters` and related OLTP tables.

**Target:** `fact_encounters`

**Grain:** One row per source encounter.

The encounter fact table is the central fact table in the warehouse.

**Approach:**

1. Extract all encounters from the source `encounters` table.
2. Look up the corresponding patient, provider, specialty, department, and encounter type surrogate keys.
3. Look up the encounter date key from `dim_date`.
4. Look up the discharge date key when a discharge date exists.
5. Retrieve the primary diagnosis key.
6. Preserve the original encounter and discharge timestamps.
7. Retrieve the pre-aggregated diagnosis, procedure, and billing metrics from staging tables.
8. Calculate encounter duration and patient age at the encounter date.
9. Identify index admissions.
10. Insert each encounter into `fact_encounters`.

The ETL uses `LEFT JOIN` operations for dimension lookups and applies `COALESCE(..., -1)` when a corresponding dimension record is unavailable.

This ensures that encounters can still be loaded using the unknown dimension member instead of being excluded because of missing dimension relationships.

### 3.2 Staging and Pre-Aggregation

Before loading `fact_encounters`, the ETL creates three temporary staging tables.

Each staging table aggregates its source records independently to one row per encounter.

**A. `stg_dx` — Diagnosis Metrics**

Source: `healthcare_analytics.encounter_diagnoses`

Calculates:

- `diagnosis_count` — number of diagnoses associated with an encounter.
- `primary_diagnosis_id` — diagnosis identifier associated with diagnosis sequence 1.

**B. `stg_px` — Procedure Metrics**

Source: `healthcare_analytics.encounter_procedures`

Calculates:

- `procedure_count` — number of procedures associated with an encounter.

**C. `stg_bill` — Billing Metrics**

Source: `healthcare_analytics.billing`

Calculates:

- `claim_count` — number of billing records associated with an encounter.
- `total_claim` — total claim amount associated with an encounter.
- `total_allowed` — total allowed amount associated with an encounter.

Each staging table is aggregated independently before being joined to the encounter records.

This is important because directly joining diagnosis, procedure, and billing records could multiply rows and produce incorrect counts and financial totals.

### 3.3 Measures Stored in `fact_encounters`

The encounter fact table contains the following pre-aggregated measures:

| Measure | Description |
|---|---|
| `diagnosis_count` | Number of diagnoses associated with the encounter. |
| `procedure_count` | Number of procedures associated with the encounter. |
| `claim_count` | Number of billing records associated with the encounter. |
| `total_claim_amount` | Total claimed amount associated with the encounter. |
| `total_allowed_amount` | Total allowed billing amount associated with the encounter. |
| `length_of_stay_hours` | Encounter duration in hours when the discharge date is valid. |
| `length_of_stay_days` | Difference between discharge date and encounter date in days. |
| `patient_age_at_encounter` | Patient's age at the time of the encounter. |

The billing measures are aggregated from the OLTP `billing` table and stored directly in `fact_encounters`.

The current implementation does not create a separate `fact_billing` table. Individual billing records remain in the OLTP database, while their encounter-level totals are stored in the warehouse fact table.

### 3.4 Handling Missing Data

The ETL applies the following rules:

- **Missing dimension relationship:** Use surrogate key `-1` where the fact table has a corresponding unknown dimension member.
- **Missing encounter date:** Use the unknown date key if no matching date is found.
- **Missing discharge date:** Use the unknown date key when no matching calendar date is available; preserve the original discharge timestamp as `NULL`.
- **Missing diagnosis associations:** Set `diagnosis_count` to `0` and use the unknown diagnosis key when no primary diagnosis is available.
- **Missing procedure associations:** Set `procedure_count` to `0`.
- **Missing billing associations:** Set claim count and billing totals to `0`.
- **Invalid or unavailable patient age:** Store `NULL` when the calculated age falls outside the accepted range of 0–130 years.

The ETL uses `LEFT JOIN` operations to retain encounter records even when optional relationships or descriptive dimension records are missing.

## 4. Readmission Calculation

Readmission indicators are calculated during ETL rather than repeatedly calculated in analytical reports.

### 4.1 Identifying Index Admissions

The ETL identifies an index admission when:

- The encounter type is Inpatient.
- The encounter has a non-null discharge date.

The resulting indicator is stored in `fact_encounters.is_index_admission`.

### 4.2 Identifying 30-Day Readmissions

The ETL creates temporary staging tables:

- `stg_ip` — contains inpatient encounters.
- `stg_ip2` — a copy of the inpatient staging data.
- `stg_readmit` — contains qualifying index admissions and their next admission dates.

For each index admission, the ETL searches for the first subsequent inpatient encounter for the same patient.

The next admission must satisfy the following conditions:

1. It belongs to the same patient.
2. Its encounter timestamp is later than the index admission's discharge timestamp.
3. It occurs within 30 days after discharge.

The first qualifying subsequent admission is identified using `MIN(encounter_datetime)`.

### 4.3 Readmission Indicators

The ETL updates the fact table with the following indicators:

- `is_readmitted_30d` — set to TRUE when an index admission is followed by a qualifying inpatient admission within 30 days.
- `days_to_next_admission` — stores the number of calendar days between discharge and the next inpatient encounter.
- `is_readmission` — identifies encounters that qualify as subsequent readmissions following an index admission.

These indicators support readmission analysis without requiring analytical queries to repeatedly perform self-joins on the encounter fact table.

**Important business-rule distinction:** The implemented readmission calculation uses inpatient-to-inpatient admissions. It is therefore narrower than a calculation that considers any subsequent encounter type.

## 5. Bridge Table Load Logic

### 5.1 Loading `bridge_encounter_diagnoses`

**Source:** `healthcare_analytics.encounter_diagnoses`

**Target:** `bridge_encounter_diagnoses`

**Approach:**

1. Extract encounter–diagnosis associations.
2. Retrieve the corresponding `encounter_key`.
3. Retrieve the corresponding `diagnosis_key`.
4. Generate a diagnosis sequence using `ROW_NUMBER()`.
5. Identify the primary diagnosis using the source diagnosis sequence.
6. Insert the resulting relationships into the bridge table.

The generated sequence is ordered by the original diagnosis sequence and `encounter_diagnosis_id`.

The bridge table preserves the many-to-many relationship between encounters and diagnoses without duplicating encounter-level fact records.

### 5.2 Loading `bridge_encounter_procedures`

**Source:** `healthcare_analytics.encounter_procedures`

**Target:** `bridge_encounter_procedures`

**Approach:**

1. Extract encounter–procedure associations.
2. Retrieve the corresponding `encounter_key`.
3. Retrieve the corresponding `procedure_key`.
4. Generate a procedure sequence using `ROW_NUMBER()`.
5. Look up the procedure date key.
6. Use the encounter date key as a fallback when the procedure date is unavailable.
7. Insert the resulting relationships into the bridge table.

The generated sequence is ordered by procedure date and `encounter_procedure_id`.

This preserves multiple procedure occurrences associated with the same encounter.

## 6. Pre-Aggregated Diagnosis–Procedure Combinations

### 6.1 Loading `agg_dx_px_pairs_monthly`

**Source:** `fact_encounters`, `bridge_encounter_diagnoses`, and `bridge_encounter_procedures`

**Target:** `agg_dx_px_pairs_monthly`

**Purpose:** Improve the performance of diagnosis–procedure combination analysis.

**Approach:**

1. Join encounter fact records with diagnosis bridge records.
2. Join the same encounters with procedure bridge records.
3. Group the results by encounter month, diagnosis, and procedure.
4. Count distinct encounters for each combination.
5. Insert the aggregated results into the monthly aggregate table.

The table stores:

- `year_month_key`
- `diagnosis_key`
- `procedure_key`
- `encounter_count`

The aggregation uses `COUNT(DISTINCT encounter_key)` to avoid counting the same encounter more than once for a given diagnosis–procedure combination.

This pre-aggregation reduces the work required by Query 2, which identifies the most frequent diagnosis–procedure combinations.

## 7. Refresh Strategy

### 7.1 Current Full-Refresh Approach

The current ETL uses a **full-refresh loading strategy**.

At the beginning of each execution, it truncates the warehouse tables in dependency order, including:

- Aggregate tables.
- Bridge tables.
- Fact tables.
- Dimension tables.

The script then rebuilds the warehouse from the OLTP source.

`TRUNCATE TABLE` also resets the AUTO_INCREMENT surrogate keys.

This approach is suitable for the current project dataset because it ensures that the warehouse is rebuilt consistently from the available source data.

The ETL is safe to rerun in the sense that it empties and rebuilds the warehouse rather than appending duplicate records. However, it is not an incremental loading process.

### 7.2 Future Incremental Loading

As the dataset grows, incremental loading could reduce the amount of data processed during each ETL execution.

A future incremental approach could:

1. Identify new or modified source records.
2. Use reliable change-tracking mechanisms such as `updated_at` timestamps, Change Data Capture (CDC), or change logs.
3. Load new records and update affected warehouse records.
4. Track the last successfully processed batch or extraction watermark.
5. Recalculate affected aggregates and readmission indicators.
6. Validate the results before marking the batch successful.

Incremental loading is not implemented in the current script.

### 7.3 Late-Arriving Data

Late-arriving data refers to source records that become available after an earlier ETL execution.

For example, billing information or a diagnosis association may be added after the corresponding encounter has already been recorded.

**Current behavior:**

- The next full-refresh execution reads the available source data again.
- Newly available billing, diagnosis, and procedure records are included in the rebuilt warehouse.
- Related encounter-level measures and monthly diagnosis–procedure aggregates are recalculated.
- There is no separate late-arriving-record queue because the full-refresh process rebuilds the warehouse from the source.

A future incremental implementation would need explicit mechanisms to identify and retry affected records.

## 8. ETL Batch Logging and Validation

### 8.1 ETL Batch Logging

The ETL uses the `etl_batch_log` table to track execution information.

At the beginning of the ETL process:

1. A new batch record is inserted.
2. The generated `etl_batch_id` is stored in the session variable `@batch`.
3. The batch identifier is assigned to fact records through `etl_batch_id`.

At the end of the process, the batch record is updated with:

- `finished_at` — ETL completion timestamp.
- `status` — set to `SUCCESS`.
- `rows_inserted` — number of records in `fact_encounters`.
- `high_watermark` — latest encounter date found in the source database.

This provides basic execution tracking and identifies which ETL batch loaded the encounter records.

### 8.2 Reconciliation Checks

The final ETL section performs four reconciliation checks.

The checks compare:

| Validation | Comparison |
|---|---|
| Missing encounters | Source encounter count versus fact encounter count. |
| Allowed amount difference | Total source allowed amounts versus total allowed amounts in the fact table. |
| Diagnosis row difference | Source diagnosis association count versus diagnosis bridge row count. |
| Procedure row difference | Source procedure association count versus procedure bridge row count. |

The expected difference for each check is `0`.

These checks help verify that the ETL has retained the source encounters, billing totals, diagnosis relationships, and procedure relationships.

The script also re-enables foreign key checks after loading the warehouse.

**Note:** The reconciliation checks are basic validation checks. They do not independently validate every dimension attribute, every individual billing record, all claim amounts, or every readmission indicator.

## 9. Performance and Execution Considerations

The ETL is designed for MySQL 8.0+ and includes several execution settings:

- Temporarily disables `sql_safe_updates` to permit the required multi-table updates.
- Temporarily disables foreign key checks during the bulk-loading phase.
- Increases `cte_max_recursion_depth` to support generation of the complete calendar range.
- Uses temporary staging tables to reduce repeated aggregations.
- Uses independently aggregated staging tables to prevent join fan-out.
- Calculates readmission indicators once during ETL instead of repeating the self-join in every report.
- Builds a monthly diagnosis–procedure aggregate table to accelerate analytical queries.

After the loading process, foreign key checks and the original `sql_safe_updates` setting are restored.

For MySQL Workbench, the database connection read timeout may need to be increased for large ETL executions.

## 10. Conclusion

The implemented ETL process transforms the normalized healthcare OLTP database into a dimensional data warehouse centered on `fact_encounters`.

It loads descriptive dimensions, generates a continuous date dimension, handles unknown dimension values, and uses temporary staging tables to calculate encounter-level diagnosis, procedure, and billing metrics.

The process also calculates readmission indicators, preserves diagnosis and procedure relationships through bridge tables, and builds a monthly diagnosis–procedure aggregate table for faster analytical reporting.

The current implementation uses a full-refresh strategy and includes batch logging and basic reconciliation checks.

Overall, the ETL process supports the four analytical queries while reducing repeated calculations, preserving important source relationships, and improving the performance of healthcare analytics reporting.
